Launcher contracts before Swift

3sx-launcher · October 7, 2026

Actual game launches reproduced boolean rejection, an unread VSync setting, and exit-time overwrite. A native Swift host is feasible; its build speed has not been measured.

Concentrate the engine settings contract

Strong

01

The UI, INI writer, and game each assume different value and persistence rules. Successful disk writes do not mean applied or durable game settings.

Solution

Establish one documented, engine-verified settings contract before porting persistence: exact types and input tokens, startup-only behavior, and explicit ownership while the game runs.

Benefits

Fix the existing product rather than copying broken behavior into a new language.

Locality: engine value and lifecycle knowledge in one placeLeverage: covers all settings and both native hostsTest surface: real engine effects and durable saves

Replace the macOS host with Swift, retaining React

Worth exploring

02

The host is filesystem, HTTP, hashing, subprocesses, and a 14-command/one-event frontend interface. No essential Rust-only capability was identified.

Solution

Port the macOS native responsibilities to Foundation/AppKit/CryptoKit and WKWebView with an explicit new bridge; migrate frontend callers instead of emulating Tauri internals. A full SwiftUI replacement adds the entire UI rewrite.

Benefits

Removes the Rust/Tauri macOS host dependency while preserving the current interface design.

Locality: Apple-native operations in the native hostLeverage: retain React while changing native implementationTest surface: same engine, ROM, updater, and settings outcomes
high

Blast radius

Native bridge, window controls, external links, persistence, updater, ROM import, packaging. AppKit/SwiftUI are macOS-only; retaining Windows/Linux requires separate supported hosts.

Top recommendation

03

Repair and exercise the engine settings contract first. If macOS-only becomes the product decision, a Swift/AppKit host retaining React is the smaller clean cutover; otherwise account for the maintained non-macOS backend. Do not promise faster total CI from the current macOS timings alone.
